# DataAir — Knowledge Engineering Platform (v1 Summary)

## Overview

DataAir is a self-hosted platform for turning documents into a searchable, citable knowledge base. Upload files, let the platform chunk and embed them, then ask questions and get answers with citations back to the source passages.

**Stack**: FastAPI backend, Next.js frontend, Airflow for orchestration, dbt for warehouse transformations, Great Expectations for data quality, OpenMetadata for lineage.

---

## Architecture

### Service Groups

**Application Group** (serves user requests):
- nginx (edge, port 80)
- FastAPI backend (port 8000)
- Next.js frontend (port 3000)
- Celery worker + Beat scheduler

**Pipeline Group** (prepares data):
- Airflow (scheduler, webserver, triggerer)
- dbt
- Great Expectations
- OpenMetadata (catalog + lineage)

**Data Stores**:
- PostgreSQL (app + warehouse, pgvector)
- Redis (broker, cache)
- MinIO (object storage)
- Qdrant (vector DB)
- Elasticsearch (full-text search)

**Observability**:
- Prometheus (metrics)
- Grafana (dashboards)

**Key Structural Fact**: The backend is the only service the browser talks to. Everything else is initiated by the backend or runs on a schedule and writes to Postgres, which the backend then reads.

## Core User Flows

### 1. Sign Up
- POST `/auth/register` → creates tenant (workspace), user (admin if in ADMIN_EMAILS), subscription (free plan)
- Returns access + refresh + CSRF cookies

### 2. Create Knowledge Base & Upload Document
- POST `/knowledge-bases/` → creates KB
- POST `/documents/upload` (multipart) → extracts, cleans, normalizes, chunks (800 chars/100 overlap), extracts entities from first 1000 chars
- Stores chunks in DB, status = processed

### 3. Index (Chunk, Embed, Register)
- **Two chunkers exist**:
  - `TokenChunker` (300 tokens/50 overlap) — used by indexing task, stable chunk IDs
  - `Chunker` (800 chars/100 overlap) — used by upload endpoint, positional only
- Embeddings: OpenAI API (1536/3072 dims) or offline hashing trick (384 dims, deterministic)
- LRU cache of 2048 entries keyed by `model:text`
- Hybrid index: VectorIndex (cosine similarity) + KeywordIndex (term frequency) + MetadataIndex

### 4. Search
- POST `/api/v1/search/` with query + limit
- Over-fetches (limit × 2), merges keyword + vector scores (0.4/0.6 weights)
- Metadata filter (exact match), then reranker (0.5×hybrid + 0.3×lexical + 0.1×position + 0.1×length)
- Four endpoints: hybrid, keyword-only, vector-only, graph-only

### 5. RAG/Chat
- POST `/rag/` or `/chat` (streaming SSE)
- Retrieves top passages → ContextBuilder (dedupe → filter → compress to 500 chars → order → 4000 token budget) → LLMGateway
- LLMGateway chains: OpenAI → Anthropic → Google → Ollama → Offline
- Extractive fallback if all providers fail
- Chat is public, rate-limited (20 req/60s per user/IP)

## Accounts & Access

- **Tenant** = isolation boundary (users, KBs, documents, API keys, work groups, billing)
- **Roles**: GUEST, MEMBER, ADMIN
- **Auth**: JWT tokens (24h access, 30d refresh, rotating), bcrypt passwords
- **API Keys**: `dk_`-prefixed, stored as prefix + HMAC-SHA256 hash
- **CSRF**: Double-submit cookie, exempt for `/auth/*`, `/chat`, `/contact`, billing webhook, API key/Bearer auth

## Indexing & Search Implementation

### Two Chunking Paths (Critical)
| Aspect | TokenChunker (indexing) | Chunker (upload) |
|--------|------------------------|------------------|
| Granularity | 300 tokens, 50 overlap | 800 chars, 100 overlap |
| Chunk ID | `doc_id:index` (stable) | positional only |
| Carries | start_char, end_char, token_count | raw text |

**The upload path stores chunks; the indexing path embeds them. Nothing connects the two yet.**

### Index Structure (per-process singleton)
- `KeywordIndex`: term frequency damped by length
- `VectorIndex`: cosine similarity via numpy over every embedding
- `MetadataIndex`: exact-match filter registry
- `GraphIndex`: substring match on entity names
- `HybridIndex`: blends keyword (0.4) + vector (0.6) over shared chunk keys

### Retrieval Engine
- Candidate multiplier: 4×
- Reranker: 0.5×hybrid + 0.3×query-term overlap + 0.1×position + 0.1×length
- Accepts `kb_ids` and `score_threshold` but ignores them

---

## RAG Pipeline

1. `RetrievalEngine.search()` → ranked passages
2. `ContextBuilder.build()`:
   - Deduplicate by chunk, then document
   - Drop low-relevance (< 0.1 score)
   - Compress each to 500 chars
   - Order by relevance
   - Budget: 4000 tokens (word-count approximation)
3. `LLMGateway.generate()` with numbered passages + citation instruction
4. Fallback: extractive (quote passages verbatim)

---

## LLM Gateway

Multi-provider with graceful degradation:
- Providers: OpenAI, Anthropic, Google Gemini, Ollama, Offline
- Chain resolution: pinned `LLM_PROVIDER` → auto (configured + available) → offline
- Streaming: SSE with `meta` (provider/model), `delta` (chunks), `done` (latency/tokens), `error`
- If provider fails before any token → try next; if mid-stream → propagate error
- Offline responder tells which env vars would enable real models

## Background Pipelines (Airflow)

```
MinIO (CSV) → ingest_minio_landing (*/30) → raw.sales/products/customers
  → warehouse_build (02:00, dbt clean→deps→build) → staging → marts.sales_daily (incremental)
  → data_quality_check (03:30, Great Expectations) → audit.elt_runs/data_quality_results
  → catalog_sync (04:00) → OpenMetadata (lineage + glossary)
```

- Airflow never calls the API; shares only Postgres
- Backend can trigger/pause DAGs but no DAG calls back
- Celery queues: `default`, `indexing`, `ingestion`; beat schedules tenant-refresh every 15min

## Configuration

All via environment variables (`.env` gitignored, `.env.example` committed).

**Key Groups**:
- Database: `DATABASE_URL` (use `ssl=require`, not `sslmode=require`)
- Auth: `JWT_SECRET_KEY`, `CSRF_SECRET_KEY`, `API_KEY_HMAC_SECRET`, `ADMIN_EMAILS`, `COOKIE_SECURE`
- LLM: `LLM_PROVIDER`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, `OLLAMA_BASE_URL`, `LLM_OFFLINE_FALLBACK`
- Chat: `CHAT_RATE_LIMIT_*`, `CHAT_SYSTEM_PROMPT`, `CHAT_TEMPERATURE`, `CHAT_MAX_TOKENS`
- Platform: `MINIO_*`, `QDRANT_URL`, `ELASTICSEARCH_URL`, `AIRFLOW_*`, `OPENMETADATA_*`, `ALLOWED_ORIGINS`

**Production Gate** (`APP_ENV=production`): validates all secrets set, `COOKIE_SECURE=true`, `ADMIN_EMAILS` non-empty, no CORS `*`.

## Implementation Status (Critical)

| Area | State |
|------|-------|
| Tenants, users, sessions, CSRF, admin, work groups, profiles, billing, API keys | Postgres + SQLAlchemy |
| `tenants`, `knowledge-bases`, `documents`, `workflows`, `metadata` routers | **In-memory dicts** (process lifetime, tenant-scoped) |
| `chunks`, `entities`, `relationships`, `sources`, `evaluation_*`, `metadata_schemas` tables | Declared in models, **never written** |
| Indexing | `dataair.index.document` task exists but **nothing dispatches it** |
| Cross-process visibility | `hybrid_index` is per-process singleton; API and worker are separate containers |
| `POST /documents/upload` | Extracts, chunks, stores — **never indexes** |
| Qdrant, Elasticsearch | Health-probed only; **never written** |
| API keys | Minted/hashed correctly, **no dependency resolves x-api-key to user** |
| `ApiUsageLog` | Read by usage endpoints, **never written** (reports zero) |
| Alembic | Wired into `make migrate` but no versions; schema from `init_db()` |
| Search scoping | `kb_ids`, `score_threshold` accepted and ignored |
| Result shapes | `SearchResult` requires `chunk_id`/`document_id`/`title`/`score`; index emits `doc_id`/`hybrid_score` |

**Read this table before estimating work on search/RAG.**

## Key Technical Debt / Gaps

1. **Upload ≠ Index**: Documents uploaded via UI are stored but not searchable until Celery task runs (and nothing triggers it)
2. **In-memory routers**: Knowledge bases, documents, workflows, metadata use process-local dicts — not persisted across restarts or visible across containers
3. **No external index write**: Qdrant/Elasticsearch configured but never used; vector search is numpy linear scan
4. **API key auth broken**: Header waives CSRF but still fails authentication (no dependency resolves key → user)
5. **Search scoping ignored**: `kb_ids`, `score_threshold` accepted but not applied
6. **Schema mismatch**: `SearchResult` model expects fields the index doesn't produce
7. **Alembic not used**: Migrations declared but schema created by `init_db()`
8. **Worker/API index isolation**: Each container has its own `hybrid_index`; worker indexes are invisible to API
